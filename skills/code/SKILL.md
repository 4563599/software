# lyycode：提交逐文件验证网页

把一笔提交的每一处代码修改，整理成一张可以逐项核对的网页。读的人是要动手验证的开发或测试：他要知道每个文件改了什么、每句代码是什么意思、为什么这样改、在 App 里怎么点进去验证。

脚本 `scripts/lyycode.js` 负责机械的部分（读 git、切分变更、校验、套模板生成网页），你负责写说明。只需要 Node.js 和 git，不需要 Python。

## 输出长什么样

一张静态网页（内容直接写在 HTML 里，不执行脚本也能完整显示）：

- 左侧是文件列表，顺序和 git 显示的一样：序号、文件名，右边是勾选方框（没勾显示「未验证」，打勾后变成绿色 ✓「已验证」）。点文件名跳转。列表里不显示 +/− 行数。每个文件栏右侧也有同样的方框，两处同步。
- 主体按文件分组。每个文件上方有一条文件栏（序号、文件名、目录、几处变更、勾选方框），下面每处变更（git 的一个 hunk）占两行：
  1. **第一行：具体代码变更**（占满整行）：代码框里完整显示这处变更的代码，带新旧行号，新增行绿色、删除行红色。代码不换行，太长的行在代码框内左右滚动。**代码含义直接写在代码行后面**，像 `// 先记下改之前是不是地图场景` 这样的注释，同一处变更里的注释对齐。**导包类变更默认折叠**，只显示一行「导包 · N 行改动（点击展开）」。
  2. **第二行：左右两列**
     - 左列（约 60%）**修改原因（为什么这样改）**：只放两块——「Kotlin 语法」（这处变更用到的语法：语法名、文档章节 › 小节 · 页码、解释）和「为什么这样改」。
     - 右列（约 40%）**如何验证（页面如何进入）**：从哪个页面怎么点进去，做什么操作，应该看到什么。
- 没有表头，每个格子自己带标题「变更 ① · 修改原因」「变更 ① · 如何验证」。
- 页面顶部是提醒框：读代码时发现的问题、测试前要准备的东西。

## 步骤

### 1. 确认范围和需求依据

需要知道三件事，对话里已经有的就不要再问：

- **仓库路径**，以及**哪笔提交**（或提交范围 `A..B`）。没说提交时默认 `HEAD`。
- **需求依据**：PRD、需求文档、设计稿、用户在对话里做过的决定。「为什么这样改」必须有出处，所以先把这些读一遍。
- **输出位置**：网页默认生成到 `E:\codeexplain`，文件名是「时间_提交信息.html」，时间格式 `yyyyMMddhhmm`、小时用 12 小时制（下午 5:37 写作 `0537`），例如 `202611110537_弱化Evchargo App的运营板块.html`。脚本自动处理，不用自己拼。用户指定了别的位置才用 `--out`（完整文件路径）或 `--out-dir`（目录）。中间文件（hunks.md、notes.json）放在脚本默认的临时工作目录，不要写进代码仓库。

### 2. 导出变更清单

```bash
node <技能目录>/scripts/lyycode.js hunks --repo <仓库> --commit <提交>
```

提交范围用 `--range A..B` 代替 `--commit`。脚本会打印两个文件的路径：

- `hunks.md`：每个文件、每处变更的代码，按 git 顺序编号。
- `notes.json`：待填写的骨架，已经按文件和变更排好位置。导包类变更已经自动填好。

把 `hunks.md` 从头到尾读完再动笔。只看片段不够时，用 `git show <提交>:<文件路径>` 看完整文件，用 `git grep` 找调用方。**代码一律通过 git 读，不要读工作区里的文件**：工作区的文件可能被公司加密软件加密，也可能带着未提交的改动，和提交里的内容不一样。

### 3. 查 Kotlin 文档，确定每个语法的出处

**每次都要做，不能凭记忆写语法解释。** 页面上每个语法都要标出它在本地 Kotlin 官方中文文档（`E:\学习\kotlincn-docs.pdf`）里的章节和页码，读的人可以翻到原文核对。

1. 读完 `hunks.md` 后，把代码变更里用到的 Kotlin 语法列出来（`?.`、`?:`、`let`、`when`、`companion object`、`suspend` ……）。
2. 先查 `references/kotlin-syntax-index.md`，表里有的直接用它的「章节 › 小节 · 页码」。
3. 表里没有的，用脚本搜已切分好的文档，确认章节和页码：
   ```bash
   node <技能目录>/scripts/kotlin-docs.js find <关键字...> --chapter <章节名片段> --max 5
   ```
   中文搜不到时换英文再搜（文档有些段落没翻译）。查到后把这一行补进索引表，下次直接用。
4. 只看搜索返回的几行上下文；需要更多内容时读 `references/kotlin-docs/chapters/` 里对应章节文件的那几页。**不要用 Read 打开 PDF 逐页读**，太慢也太费 token。
5. `references/kotlin-docs/` 不存在或 PDF 更新了，先运行 `node <技能目录>/scripts/kotlin-docs.js build "E:\学习\kotlincn-docs.pdf"`（约 10 秒）。
6. 确实是 Android 或第三方库的内容（文档里搜不到），文档位置写「文档未收录（Android / 第三方库）」。

### 4. 填写 notes.json

每处变更写一项，字段如下（完整例子见 `references/notes-example.json`）：

| 字段 | 含义 |
|---|---|
| `why` | 为什么这样改。可以用 `<br>`、`<code>`、`<b>`。必填。 |
| `verify` | 如何验证，包括页面怎么进入。必填。 |
| `lines` | 每行代码后面的说明，`{"代码行": "说明", ...}`。`kind` 是 `code` 的变更要写。纯文本，脚本会转义。 |
| `syntax` | 这处变更用到的语法，`[["语法名", "文档位置", "解释"], ...]`。`kind` 是 `code` 的变更要写。 |
| `warn` | 这处变更有问题时设为 `true`，页面上会标红。 |
| `hunk` / `start` / `kind` | 骨架自带，方便对照 `hunks.md`，不用改。 |

顶层还有 `title`（页面标题）和 `alerts`（顶部提醒框，`{"type": "warn" 或 "info", "html": "..."}`）。

导包（`kind` 是 `import`）的变更在页面上默认折叠，骨架已经自动填好 `why` 和 `verify`，不用写 `lines` / `syntax`。布局、图标等资源文件（`kind` 是 `resource`）也不写逐行说明，只写 `why` 和 `verify`。

**怎么写 `lines`（每行代码的含义）**

- key 是代码行**去掉行首的 +/- 和首尾空格**后的原文，从 `hunks.md` 里复制，一个字符都不能差；value 是这行的说明。脚本会把说明显示在这行代码后面，形如 `// 先记下改之前是不是地图场景`。
- 同一处变更里有一模一样的两行时（比如删除的 `toMainPage()` 和新增的 `toMainPage()`），在 key 前加 `"+ "` 或 `"- "` 指定是新增行还是删除行。
- 同样的代码出现多次、但要写不同说明时，value 写成数组，按出现顺序对应：`"toLastScenarioPage()": ["注册成功：按场景进首页", "绑定邮箱成功：按场景进首页"]`。数组里写 `null` 表示那一次不加说明。value 是字符串时，所有相同的行都用这条说明。
- 写哪些行：新增、删除、改动的代码行都要写；被注释掉的旧代码，在这段的第一行写「注释掉：原来……」；花括号、空行、本身就是中文注释的行不用写；没改动的上下文行一般不写。
- 说明要短（一般 20 个字以内），说出这行代码在这里的作用，而不是翻译语法。比如 `return` 写「后面的初始化、版本检查都不执行」，不要只写「返回」。
- key 对不上代码行时，脚本会报错并列出对不上的 key，按提示改了再生成。

**怎么写 `syntax`（Kotlin 语法）**

- 每个元素 `["语法名", "文档位置", "解释"]`。把这处变更里用到的、值得给不熟悉 Kotlin 的人解释的语法都列出来，同一个语法只写一次。
  - **语法名**：用文档里的叫法，比如「安全调用 ?.」「Elvis 操作符 ?:」「拖尾 lambda」「伴生对象」「编译期常量」「具名实参」。
  - **文档位置**：按第 3 步查到的「章节 › 小节 · 第 N 页」。
  - **Android / 第三方库的内容**（`lifecycleScope`、`LiveData.postValue`、DataBinding 生成的属性、Retrofit 注解、`requireContext()` 等）文档里没有，文档位置写「文档未收录（Android / 第三方库）」，再用自己的话解释。
  - **解释**：一两句话，说清楚这个语法在这段代码里的作用，可以和 Java 对比（比如「相当于 Java 的 static」）。用自己的话写，不要大段照抄文档原文。
  - 文件不是 Kotlin 时（.java、.dart 等），页面自动标成对应语言；文档位置留空或写对应语言的资料。
- 每处代码变更至少要有一个语法项，没有时脚本会提醒。
- 同一个语法在同一个文件里已经解释过，后面可以简短带过。

**Kotlin 文档在本地的位置**

- 原始 PDF：`E:\学习\kotlincn-docs.pdf`（2184 页）。
- 已切分的文本：`references/kotlin-docs/`。`chapters.tsv` 是章节和页码的对照，`chapters/` 下每章一个文本文件，每页前有 `[p.页码]` 标记。
- 文档更新后重新切分一次（约 10 秒，需要 Git for Windows 自带的 pdftotext）：
  ```bash
  node <技能目录>/scripts/kotlin-docs.js build "E:\学习\kotlincn-docs.pdf"
  ```
- 被注释掉的旧代码也要解释：说明原来这句是做什么的。
- 没有改动的上下文行不用解释。
- **导包、布局文件、图标和其它资源 / 配置文件不逐句解释**（骨架里 `kind` 是 `import` 或 `resource`），只写 `why` 和 `verify`。这类内容逐句解释只会把页面撑长，读的人并不需要。

**怎么写 `why`（为什么这样改）**

- 写出依据：对应 PRD 的哪一节、哪张设计稿、用户的哪个决定，再说明为什么选这种实现方式。
- 不要推断。在需求和代码里都找不到原因时，照实写「需求里没有说明原因，需要确认」，并在最终回复里列出来，不要编一个听起来合理的理由。
- 保留但不再引用的旧代码，说明它是哪个旧方案留下的、为什么保留。

**怎么写 `verify`（如何验证）**

- 从用户能看到的入口写起，用「→」连接每一步，最后写预期结果。例如：`Me → 个人信息 → 退出登录 → 登录页按返回 → App 退出`。
- 有多种情况时用 ①②③ 分开，各写一行（`<br>` 换行）。
- 需要抓包、看日志、换账号、断网的，写清楚抓哪个接口、过滤什么关键字。
- 纯导包这类变更写「编译通过即可」。只能靠看代码确认的，写「代码检查：……」并说清楚检查什么。

**读代码时发现的问题**

逐处读代码时经常会发现问题，比如注释标记不完整、约定要注释保留的代码被直接删了、新逻辑在某条路径上有副作用。这些正是验证方案最有价值的部分：

- 在对应变更上设 `"warn": true`，并在 `why` / `verify` 里写清楚问题和现状。
- 在 `alerts` 里加一条 `warn`，让读的人一打开就看到。
- 测试前的准备（测试账号、抓包接口、日志关键字、这次没做的需求）放进一条 `info` 类型的 `alerts`。
- 只报告，不要顺手改代码，除非用户要求。

### 5. 生成网页并检查

```bash
node <技能目录>/scripts/lyycode.js build --repo <仓库> --commit <提交>
```

- 脚本会校验：每个文件的说明条数和变更处数一致、`why` / `verify` 不为空。有问题会列出来并且不生成，改完 `notes.json` 再跑。
- 「提醒」里列出的是代码变更却没有逐句解释的地方，逐条补上，或者确认它确实不需要。
- 网页默认生成到 `E:\codeexplain\时间_提交信息.html`，路径在脚本输出的「已生成」那一行。用 `--out <文件路径>` 或 `--out-dir <目录>` 可以改位置。
- 生成后看一眼页面再交付。机器上有 Chrome 时可以无界面截图检查：
  `chrome --headless=new --window-size=1600,1200 --screenshot=<图片路径> file:///<网页路径>`
  重点看：页面没有被撑宽；每处变更是“代码一行 + 原因 | 验证两列一行”；代码没有换行、代码行后面有 `//` 说明；导包变更是折叠的；原因只有「Kotlin 语法」和「为什么这样改」；左侧文件列表右边是勾选方框。

### 6. 交付

告诉用户：

- 网页的完整路径（有发送文件的工具就直接发过去）。
- 文件数、变更处数、增删行数（脚本输出里有），方便和 git 对一下。
- 读代码时发现的问题，逐条列出。
- 哪些地方的修改原因没有依据、需要确认；哪些检查没有做（比如没有截图看过页面）。

## 约定

- 页面和说明都用中文，句子写完整，少用缩写和内部代号。读的人可能没有参与开发。
- 文件顺序、变更顺序都跟 git 保持一致，不要按功能重排。用户要拿它和 git 逐个对照。
- 不要改 `assets/template.html` 的结构来迁就某一次的内容。确实要调整版式时改模板本身，让以后每次生成都一致。
- 同一笔提交重新生成时，`hunks` 不会覆盖已有的 `notes.json`（加 `--force` 才覆盖），所以可以放心重跑。
