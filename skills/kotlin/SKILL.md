# Kotlin 编码规范

以用户指定的 [Kotlin 编码规范](https://book.kotlincn.net/text/coding-conventions.html) 为规范依据。名称保持为 `kotlin`。

## 规范正文与额外说明

- [编码规范正文](references/coding-conventions.md)：保留网页原有章节名称、层级和顺序，逐项整理规则、适用条件、例外与关键排版示例。不是只覆盖常用规则的摘要，也不声称逐字复制原文。
- [额外执行说明](references/execution-guidance.md)：技能运行策略与用户要求的十一条项目附加规则——临时测试清理、资源优先复用、相同字符串直接复用并按功能排列、命名简短、注释简短、提交信息只描述功能（任务完成后给出一句话的建议提交信息）且提交信息和代码里不出现 AI 工具信息、UI 按设计图实现且拿不准先反馈（提示类内容不自行添加，和设计有出入的地方不写进代码注释、实现前先确认）、不用的代码直接删除（类、无调用方法和资源保留）、只优化用户自己的代码、Figma 图片优先用 SVG 转矢量图、用户自己的 TODO 写成 `//TODO jade 内容`且任务完成时列出 TODO 总结；不属于网页规范原文。

不要将执行策略或项目个人习惯混入规范正文，也不要把它们称为 Kotlin 官方强制规则。

## 使用流程

1. 阅读额外执行说明，明确当前任务、项目约定与实际运行环境；本次涉及临时测试或资源时，执行其中对应的项目附加规则。
2. 在规范正文中读取相关章节及其例外。全面审查时通读正文；不要只读取本入口文件就宣称已按全部规范检查。
3. 保留原文的规则强度：必须、建议、优先和允许是不同要求，尤其不能把尾部逗号等可选项改成语法限制。
4. 在用户授权范围内应用规范；资源先检索再决定复用或新增，相同字符串直接复用，新增字符串放在对应功能已有字符串下面；命名和注释保持简短；新增 TODO 写成 `//TODO jade 内容`；需求变更后不用的代码和资源直接删除，不注释保留，但类、没有调用方的方法和资源文件（文字、图片、布局等）保留。只修改、优化、审查用户本人的代码，同事的代码不改、不提优化建议，只在影响用户功能时说明。
5. 做 UI 时按设计图标注实现，先找可复用的本地控件；Figma 图片优先导出 SVG 转 VectorDrawable，设计稿没提供 SVG 或转换效果不对时改用 3 倍位图（优先 WebP，其次 PNG），按项目现有目录放到 `drawable-xxhdpi` 或 `mipmap-xxhdpi`；需要扩展控件、标注无法实现或任何拿不准的地方，先反馈给用户确认再动手。实现和设计有出入或待设计确认的地方（例如“设计使用 iOS 系统字体，Android 暂用系统字体”）不写成代码注释或 TODO；实现之前先让用户确认，再按确认的方案实现。Toast、异常提示、空数据等界面提示，设计图和需求文档没写的不要自己加，先列出来让用户确认方案。
6. 提交信息只描述新增或修改的功能；提交信息和代码（含注释、资源、配置）里都不写 Claude、GPT、AI、Co-Authored-By 等工具信息。改了项目代码的任务完成时，在回复最后给出一条建议的提交信息：简洁的一句话，概括实现的功能。本次在代码里新增了 TODO 时，在建议提交信息前单独列出「TODO 总结」表格：类名（方法）、可点击的位置、TODO 原文、后面怎么做（在等什么、①②③ 步骤、怎么验证），一条都不能漏，格式见额外执行说明第 11 条。
7. 交付前检查临时测试清理、行为、兼容性与验证结果，确认代码里没有和设计相关的注释，新增的 TODO 都已列进 TODO 总结。
