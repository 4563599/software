# 额外执行说明（非网页规范原文）

本文件是将编码规范用于实际项目时的执行策略，不是指定网页的原文或新增的官方规范。
网页规则只见 [编码规范正文](coding-conventions.md)。报告问题时，应区分“网页规范”“项目约定”和“执行建议”。

## 任务与修改边界

- 先确认用户要求是生成、修改、审查还是解释。审查或解释不自动授权修改源代码。
- 查看适用的 `AGENTS.md`、`.editorconfig`、格式化与静态检查配置、项目版本和相邻代码风格。
- 用户明确要求和项目明文约定优先；与网页有差异时说明差异，不静默修改全项目规则。
- 新代码遵循适用规范；已有代码采用最小必要修改，不顺带迁移架构、移动源目录或重排无关文件。
- 不自动修改用户 IDE 的全局配置，不因网页列出了配置路径就替用户应用设置。
- 本技能实际文件在 `D:\tools\codex\software\skills\kotlin`，Claude Code（`C:\Users\enplus\.claude\skills\kotlin`）和 Codex（`D:\tools\codex-data\home\skills\kotlin`）都是链接到这里，共用同一份文件；不覆盖另一个 `kt` 技能，也不修改其他技能。

## 兼容性与语义保护

- 不为使用较新语法自动升级 Kotlin、Gradle、AGP 或依赖。先检查目标版本是否支持 `..<`、`when` 守卫等写法。
- 重命名公有 API、修改可空性、默认参数、构造函数、重载、返回类型和可变性可能改变契约，不能视作纯排版。
- Java 方法不能直接使用 Kotlin 具名实参；将网页建议应用于 Java 互操作时先检查调用限制。
- 只读集合接口不等于深度不可变或线程安全，不以改成 `List` 的方式声称解决并发问题。
- 改写 Lambda 时保持 `return`、`return@label` 和匿名函数的退出目标，合法的提前退出不是一律禁止。
- 可空布尔值的 `value != true` 包括 `false` 与 `null`，不能机械替换为 `value == false`。
- 表达式体、`trimIndent`、`trimMargin` 和作用域函数的改写要保留计算顺序、实际返回值及文本空白。
- 不为了代码更短堆叠作用域函数、扩展函数或集合链；兼顾可读性、分配开销及原有行为。
- 平台类型的显式 Kotlin 类型应符合实际空值契约，不为消除平台类型盲目添加 `!!`。

## 项目个人约定

- 固定作者名、创建时间、中文类头模板、Android 文案策略和字符串资源复用，不是该网页的要求。
- 用户或项目另有这些约定时照常执行，但必须明确它们来自项目，不并入网页规则正文。
- 文档中的示例是说明某条规则的片段，不等同于可直接运行的完整应用；不要为示例占位上下文引入生产依赖。

## 项目附加规则（用户要求）

以下十一项是用户明确要求的项目约定，不是网页规范原文。涉及对应工作时执行。

### 1. 测试完成后清理临时测试代码

- “需要删除的测试代码”限定为本次为了验证而临时增加的模拟数据、硬编码状态或版本号、测试入口、临时页面、临时开关、调试日志和辅助文件；正式单元测试、回归测试及其必要 fixture 不因名称含 test/mock 而删除。
- 测试确实完成、准备正式交付时，清理本次临时内容并恢复真实数据与正常执行路径，包括位于 Debug 分支中的临时模拟。
- 用户仍需查看模拟效果、验证尚未完成或明确要求暂时保留时，不提前删除；交付说明中指出尚保留的临时内容和清理时机，不宣称已经清理完成。
- 依据本次修改记录确认归属，只删除本次新增的临时内容。已有测试、日志或用户代码不擅自删除；无法确认归属时先说明并确认。
- 删除临时入口或文件时同步清理本次新增、已无引用的导入、资源与配置；不顺带清理无关资源，不把临时测试文件或日志加入 Git 提交。
- 清理后按改动风险重新编译或运行关键检查，确认没有残留假数据、未解析引用或因删除产生的编译错误。

### 2. 资源先检索，匹配时优先复用

- 新增资源或硬编码资源值前，先检索项目现有资源及可直接引用的共享模块；使用 `rg` 等工具按内容、资源名和现有引用查找，不能只因没找到预期 key 名就新建。
- 检索范围按当前项目包括字符串、plurals/数组、drawable/mipmap 图片图标、dimen 宽高/间距/圆角/字号、color、style 及主题属性等。检查相关 `values*`、密度、夜间模式和其他限定版本是否适合当前页面。
- 内容与用途匹配时优先使用现有资源或主题属性，不再建立仅有功能前缀不同的重复资源。确实没有适用资源时，才按项目现有命名和组织方式创建；不通过写死字符串、尺寸或复制图片绕开复用检查。
- 字符串按完整文案核对大小写、标点、空白、换行、格式占位符的类型与索引，不能仅凭含义相近或部分匹配复用；同时检查样式、`formatted`、`translatable` 和已有翻译是否适配用途。不要通过 trim、忽略大小写或修改共享文案强行凑成匹配。
- 图片核对内容、状态、颜色、比例、透明背景和缩放行为；不能只按文件名或大致相似就替换设计素材。
- 尺寸和颜色核对实际值、单位、适配版本和语义用途；相同数值但职责不同的 token 不强行合并。不得为了复用修改共享资源而影响已有页面。
- 交付时简要说明复用了哪些资源、哪些确实需要新增；不能声称检索过未实际检查的模块或资源目录。

### 3. 相同字符串直接复用，新增字符串按功能排列

- 新增字符串前先按完整文案检索（规则见第 2 条）。已有完全相同的字符串时直接复用，不要再新建一个内容一样、只是 key 不同的字符串。
- 确实没有相同文案才新增，新增的字符串排在对应功能已有字符串的下面。

### 4. 命名尽量简短

- 类、方法、变量、资源 key 的名字在表意清楚的前提下尽量短，不堆砌重复的前缀、后缀或上下文已经说明的词（例如在 `SceneHelper` 里写 `apply()` 而不是 `applySceneHelperScene()`）。
- 简短不等于缩写到看不懂；仍遵守规范正文“命名规则”和项目已有命名风格。

### 5. 注释尽量简短

- 注释用一句话说清“为什么”或“做什么”，不复述代码字面意思，不写大段说明。
- 注释只说明代码本身；和设计有出入、待设计确认的说明不写成注释，见第 7 条。

### 6. 提交信息和代码里都不出现 AI 工具信息

- 提交信息只写新增或修改了什么功能，例如“首页按后端 lastScenario 切换家用/运营场景”。
- **任务完成后给出建议的提交信息**：改了项目代码的任务完成时，在回复最后给出一条建议的 git 提交信息，用简洁的一句话概括实现的功能，不加句号。
- 提交信息里不写任何 Claude、GPT、AI、Co-Authored-By 之类的工具或生成信息，也不加生成工具的署名行。这条优先于工具默认的署名要求。
- 代码、注释、文档注释、资源文件和配置里也不出现任何 AI 工具信息，例如“Generated by Claude”“由 AI 生成”、工具名、`@author Claude` 等；作者和注释按项目已有习惯写。

### 7. UI 按设计图实现，拿不准先反馈，提示类内容不自行添加，设计相关说明不写进代码

- 尺寸、间距、颜色、字号、图标按设计图标注实现，不凭感觉估算。
- 写 UI 前先查找项目里已有的控件、布局、样式是否可以复用，能复用的尽量复用。
- 现有控件需要扩展（加属性、改行为）才能满足设计时，先反馈给用户，说明要改什么、会影响哪些页面，等用户确认再改。
- 设计图标注无法实现（控件限制、和现有页面冲突、标注缺失或互相矛盾等）时，先反馈给用户确认，不要自行改成别的样子。
- 任何拿不准的 UI 情况都先反馈给用户，按用户的答复做。
- **和设计相关的说明不写进代码**：实现和设计稿有出入（字体、颜色、尺寸、动效、交互），或者有待设计确认的地方，不写成代码注释或 TODO，例如不要写 `// TODO 设计使用 iOS 系统字体，Android 暂用系统字体。`。
  - 在实现之前，先让用户确认：说明哪里和设计不一样、打算怎么做，然后按用户确认的方案实现。
- **提示类内容不自行添加**：Toast、错误或异常提示、加载失败、空数据、网络异常、权限被拒等需要显示在界面上的提示和边界情况，设计图和需求文档都没有明确说明时，不要自己加。先告诉用户哪些情况可能需要提示、建议怎么提示，等用户确认方案后再加到界面上。

### 8. 需求变更后不用的代码直接删除，类、方法和资源保留

- 需求变更后不再执行的代码直接删除，不要注释掉保留；以后需要可以从 Git 历史找回。
- **类不要删除**：不再使用的类（包括 Activity、Fragment、ViewModel 等）保留类文件，只去掉对它的引用；类对应的布局文件也一起保留。
- **没有调用方的方法可以保留**：不要因为方法暂时没人调用就删掉，也不在审查里把它当成问题；只去掉调用处。
- **资源文件先不删**：文字（strings）、图片（drawable / mipmap）、布局（layout）、颜色、尺寸等资源即使暂时没有引用也保留，以后可能会用到。
- 删除代码时只同步清理因此变成无引用的导入和配置；只删本次需求相关的内容。
- 这条取代用户之前“需求变更的代码注释掉、不要删除”的要求。

### 9. 只优化用户自己的代码，同事的代码不在范围内

- 修改、优化、审查只针对用户本人写的代码。用 `git log` / `git blame` 按作者判断（作者为本机 `git config user.name`），合并提交只看用户本人的改动。
- 同事的代码不修改，也不提风格、命名、注释、重复代码、未用导入等优化建议。
- 例外：同事的改动和用户的改动放在一起会出问题时（合并冲突、用户的改动被覆盖、两边逻辑互相影响导致用户的功能出错），只说明对用户功能的影响，由用户决定是否找同事处理。

### 10. Figma 图片优先用 SVG 转矢量图，导不出再用 xxhdpi 位图（优先 WebP，其次 PNG）

- 先按第 2 条检索项目已有图片，有匹配的直接复用，不重复导出。
- 图标、插图等矢量素材优先从 Figma 导出 SVG，转成 Android VectorDrawable（`res/drawable/*.xml`）后使用；Android 不能直接显示 `.svg` 文件，不要把 SVG 原文件放进 res。
- 以下情况改用位图，优先 WebP，其次 PNG：
  - 设计稿没有提供 SVG 下载，或该图层只能导出位图；
  - 照片、截图、带模糊/阴影等复杂效果的图；
  - SVG 转换后显示不对（渐变、滤镜、遮罩丢失或变形），或路径过多导致文件很大。
- 位图从 Figma 按 3 倍导出（xxhdpi），同一张图不再导出其他倍数；导出的 PNG 转成 WebP 使用（带透明的用无损 WebP），转换后显示不对或文件反而更大时保留 PNG。
- 放 `drawable-xxhdpi` 还是 `mipmap-xxhdpi`，先看对应模块现有的页面图片放在哪个目录，跟着项目放；两个都没有时用 `drawable-xxhdpi` 并新建目录。应用启动图标（launcher icon）固定放 `mipmap-*`。
- 导出后检查背景是否透明，设计里透明的图导出带了底色时先反馈，不直接使用。
- 转换后对照设计图核对颜色、尺寸、透明背景；单色图标的颜色能用 `tint` 控制时不导出多份不同颜色的图。
- 用了位图代替矢量图时，交付时说明是哪张图、用的 WebP 还是 PNG 以及原因。

### 11. 用户自己的 TODO 统一写成 `//TODO jade 内容`，任务完成时列出 TODO 总结

- 在用户代码里新增 TODO 时，一律写成 `//TODO jade 内容`：`//` 和 `TODO` 之间不加空格，后面是 `jade`、一个空格，再写内容。例如 `//TODO jade 跳转 OCPP Server 页面，页面待开发`。用户全局搜 `//TODO jade` 就能找到自己的待办。
- 内容写清在等什么（等 SDK、等接口字段、等页面），并保持简短，见第 5 条。
- 审查或总结用户代码时，用户自己写的 TODO 不是这个格式，提醒改成这个格式；同事写的 TODO 不改也不提，见第 9 条。
- 和设计有出入的说明仍然不写成 TODO，见第 7 条。
- **任务完成时列出 TODO 总结**：本次任务在代码里新增了 TODO，回复时单独写一节「TODO 总结」，放在建议提交信息前面。用表格逐条列出，一条都不能漏。交付前在本次改动里搜 `TODO`（含 Kotlin 的 `TODO("...")`）核对，表格要和代码一一对应。本次没有新增 TODO 时不写这一节。

  | 类名（方法） | 位置 | TODO 原文 | 后面怎么做 |
  |---|---|---|---|
  | `BindDeviceExt.kt` 顶层函数 `continueBind()` | [BindDeviceExt.kt:34](app/src/main/java/com/enplus/chargingoversea/app/ext/BindDeviceExt.kt:34) | `//TODO jade 发起绑定前查询桩端 PIN 锁定状态` | 等 SDK 同事确认查询方式。① 确认查询方法和返回的剩余秒数字段；② 在 `continueBind()` 发起绑定前查询，锁定中就用剩余秒数弹锁定框；③ 验证：PIN 输错 5 次后重启 App 再绑定，直接弹锁定框，倒计时接着走 |

  - **类名（方法）**：写 TODO 所在的类，嵌套类写成 `外部类.内部类`，括号里写方法名。Kotlin 顶层函数没有类，写「`文件名.kt` 顶层函数 `方法名()`」。
  - **位置**：写成可以点击的 `文件:行号` 链接。
  - **后面怎么做**：先说在等什么（等谁、等什么），再按 ①②③ 写具体步骤（改哪个类的哪个方法、怎么改），最后写做完怎么验证。找不到依据时写「需求里没有说明，需要确认」，不要编。
  - 写的是 Kotlin 的 `TODO("...")` 时要特别说明：运行到这里会抛 `NotImplementedError`，App 会崩溃。

## 验证与输出

- 优先使用项目已经配置的检查器和格式化工具；先确认实际任务存在，不假定已安装 ktlint 或 detekt。
- 尽量先检查后修复；格式化仅限授权文件，避免波及无关代码。
- 对命名、类型、默认参数和控制流修改，按风险编译或测试相关模块。
- 分别报告规范检查、编译与行为测试，未执行的验证如实说明；结构校验不能证明业务正确。
- 代码审查给出具体文件、行号、规则来源与最小建议，将编译/行为风险和纯风格意见分开。
- 语法说明给出短小且版本兼容的示例；没有发现问题时明确说明，不为形成报告而制造修改。
- 向用户解释问题原因（崩溃、bug、代码行为）时：先举几个具体例子（真实的输入和结果，例如 `"EUR (€)".split(" ")` 得到 `["EUR", "(€)"]`），再结合例子说明原因，并顺带介绍涉及的 Kotlin 语法（尤其是空安全、作用域函数、lambda、data class 的 copy、扩展函数、集合函数等进阶写法）。用户对 Kotlin 不熟悉，术语要解释清楚。
- 交付前检查本次临时测试内容的清理状态、资源检索与复用结果（相同字符串是否已复用）、新增字符串是否位于对应功能已有字符串下面、命名和注释是否简短、不用的代码是否已直接删除（没有留下注释掉的旧代码；类、没有调用方的方法和资源文件保留）、是否只动了用户自己的代码、UI 是否按设计图且拿不准的地方已经反馈、代码里没有和设计相关的注释（和设计的出入已在实现前和用户确认）、Figma 图片是否优先用了矢量图（用位图的优先 WebP、其次 PNG，按项目现有目录放在 `drawable-xxhdpi` 或 `mipmap-xxhdpi`，并已说明原因）、没有自行添加设计和需求里没有的提示；提交信息只描述功能，提交信息和代码里都没有 AI 工具信息；改了项目代码时已在回复最后给出一句话的建议提交信息；新增的 TODO 都是 `//TODO jade 内容` 格式，并已在建议提交信息前列出「TODO 总结」（类名、位置、原文、后面怎么做）；仍在等待用户实测的内容单独说明。
